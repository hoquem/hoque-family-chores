# Hoque Family Chores App

An app for managing family chores, making it fun and easy to keep track of responsibilities. Built with Flutter and Firebase.

## 🚀 Planned Features

* **Cross-Platform Support**  
  * 📱 iOS  
  * 🤖 Android  

* **User Management**  
  * 🚪 Login Screen  
  * 📝 User Registration Screen  

* **Chore Management**  
  * ➕ Create Chores (with details like description, due date, recurrence)  
  * ✏️ Edit Chores  
  * 🗑️ Delete Chores  
  * 🔄 Assign Chores (or allow self-assignment)  

* **Gamification**  
  * 🏆 Points/Rewards System for completing chores  
  * 🏅 Badges or achievements  
  * 📈 Leaderboard  

* **Chore Workflow**  
  * 🙋 Family members can pick a chore  
  * 🤝 Agree on a completion date/time  
  * ✅ Mark chores as complete (possibly with a review/approval step)

## 🛠️ Development Guide

### 🔧 Adding a repository

Every data dependency goes behind an interface in the domain layer, with a
Firebase implementation in the data layer and a fake for the tests:

- **Interface** — `lib/domain/repositories/<thing>_repository.dart`
- **Firebase implementation** — `lib/data/repositories/firebase_<thing>_repository.dart`
- **Wiring** — add it to `RepositoryFactory.createRepositories()` and expose a
  provider in `lib/di/riverpod_container.dart`
- **Fake** — `test/mocks/mock_<thing>_repository.dart`, and override the
  provider with it in widget tests

#### The app always talks to Firebase

There is no mock-data mode. `RepositoryFactory` builds the Firebase
repositories unconditionally, so running the app needs a real Firebase project
and a signed-in account. The fakes live in `test/mocks/` and are reachable only
from tests, by overriding the repository providers in a `ProviderScope`.

This README used to document `flutter run --dart-define=USE_MOCK_DATA=true`.
That flag never did anything — see TASK-496.

#### Running it
```bash
flutter run          # against the configured Firebase project
flutter test         # the suite, against the fakes in test/mocks/
```

**🚨 Failure to implement both versions will result in:**
- Broken CI/CD pipelines
- Inability to test features locally
- Development bottlenecks for team members
- Inconsistent behavior between environments

### 1️⃣ Handling `pubspec.lock` Merge Conflicts
| Topic | Details |
|-------|---------|
| **What is it?** | `pubspec.lock` is the lock-file generated by `flutter pub get`. It records the exact versions of every direct and transitive dependency used in the app. |
| **Why commit it?** | • Guarantees all developers & CI use identical package versions.<br>• Enables reproducible builds.<br>• Recommended for **apps** (but not for reusable packages). |
| **When does it conflict?** | Two branches modify dependencies independently, producing different lock-file hashes. |
| **How to resolve?** | 1. Run the helper script: <br>`./scripts/resolve_pubspec_lock.sh ours` or `theirs`.<br>2. The script checks out the chosen side, runs `flutter pub get`, stages the regenerated file, and reminds you to commit.<br>3. Finish the merge or rebase as usual. |

> Tip: Always run `flutter pub get` after editing **`pubspec.yaml`** before committing, to keep the lock-file in sync.

### 2️⃣ Store Deploys (headless)

Both stores ship from one-command scripts run locally — no Xcode Cloud. They
each query the store for the highest accepted build number and build `highest+1`,
so an upload can never be rejected as a duplicate.

| Store | Command | Notes |
|-------|---------|-------|
| **TestFlight / App Store** | `scripts/deploy_testflight.sh` | Uses an App Store Connect API key; builds + uploads to the "Family" TestFlight group. |
| **Google Play** | `scripts/deploy_playstore.sh` | Uses a Play Developer API service-account JSON; builds the AAB (`targetSdk 36`) + uploads to the `internal` track. |

Run them **sequentially** (Play then TestFlight), never chained iOS-first.

### 3️⃣ Common Troubleshooting

| Symptom | Suggested Fix |
|---------|---------------|
| **Flutter package version mismatch** | Delete local `.dart_tool/` and `pubspec.lock`, run `flutter pub get`, and ensure you committed the updated `pubspec.lock`. |
| **Unit tests using real Firebase** | They shouldn't be. Tests reach Firebase only when a test forgets to override the repository providers — override them with the fakes in `test/mocks/`, as the existing widget tests do. |
| **New developer setup** | 1. Install Flutter (matching `pubspec.yaml`'s Dart constraint).<br>2. Clone repo & run `flutter pub get`.<br>3. Copy `.env.example` to `.env` and fill secrets (ask a team lead).<br>4. For iOS: `cd ios && pod install`.<br>5. Run `flutter run` on target device. |
